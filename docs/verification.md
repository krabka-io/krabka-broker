# Verification

krabka uses two formal test tiers. Creusot proves contracts for small,
executable kernels. Stateright checks all reachable states inside each model's
stated bounds. Neither tier proves the whole broker.

## Development evidence

A human maintainer and AI coding agents codeveloped krabka-broker. The
development process does not use authorship as evidence of correctness. Pull
requests apply the same build, test, proof, model-check, and compatibility gates
to human and AI changes.

An AI-generated test can repeat the implementation's mistake. krabka therefore
uses checks with independent failure signals. Mutation testing inserts faults
that the tests must detect. Creusot sends contracts to automated provers, and
Stateright explores bounded event orderings. Differential and acceptance suites
also run live, digest-pinned Kafka brokers as reference systems.

The checks do not prove the whole broker. This catalog states the formal
boundary in detail. The repository README describes the
[mutation](../README.md#mutation-testing) and
[container](../README.md#container-suites) tiers. Mutation testing stands in
for authorship only while it is actually running, so the sweeps are scheduled
weekly per crate and the
[mutation sweep baseline](mutants-baseline.md) records the last run in which
each swept crate came back with no survivor.

A mutation skip narrows that evidence, so the README's
[skipping a mutant](../README.md#skipping-a-mutant) rule bounds it. A
function-level `#[cfg_attr(test, mutants::skip)]` is accepted for an I/O-only
wrapper with no in-process signal, or for orchestration whose every branch
calls into a separately mutation-tested kernel, and it must carry a
`// cargo-mutants: <reason>` line saying which — `aspect check-mutants-skip`
fails the build otherwise. An equivalent mutant of a single expression belongs
in `.cargo/mutants.toml`'s `exclude_re` instead, so the function's other
mutants stay in the sweep. Integration coverage is explicitly not a reason: the
sweep runs unit tests and ordinary `tests/*.rs` only, so a skip resting on the
container suites removes precisely the code this tier would otherwise measure.

## Catalog Boundary

This catalog covers safety-critical, deterministic decisions implemented in
this repository. These decisions admit, reject, select, fence, order, or
recover state in KRaft, storage, security, and protocol handling. A decision
belongs in the Creusot ledger when a contract can describe its safety rule. It
belongs in the Stateright inventory when the rule depends on a bounded sequence
of events, crashes, or interleavings. Host orchestration and external systems
remain outside both tiers as described below.

The closure audit enumerated the workspace crates, traced every ledger caller
and model entry point to production code, checked its proof artifact or bounded
model and adapter tests, and searched the remaining mutation boundaries. Apart
from the barrier coordinator partitioner named under
[Outside Both Tiers](#outside-both-tiers), the audit found no unlisted decision
inside this boundary. A cross-check of the kernel source against the ledger
found every public executable function of `krabka-verified` in a ledger row,
and every kernel that a row names in the source. The tables below are the
authoritative inventory;
counts are not used because one row can contain several related kernels.

Every pull request runs the Creusot package-discovery check and all discovered
proof-bearing packages. The same CI workflow explicitly runs the five Bazel
test targets that contain every Stateright entry point in this inventory. The
explicit run is separate from impact-based test selection, so an unrelated
change cannot skip the model checks. A new proof-bearing package must pass the
discovery check. A new Stateright entry point must be added to this inventory
and to one of the explicit model-bearing targets, or that target list must be
extended.

## Creusot Proof Ledger

The [contract audit](proof-contract-audit.md) critiques every original proof
module, distinguishes decision-table contracts from aggregate invariants, and
records the remaining host assumptions. A proved implication about admission
does not establish that valid requests are accepted; admission-completeness
contracts must also rule out rejecting everything.

Creusot also creates sessions for logic functions, lemmas, private helper functions, and generated `Clone` implementations. These sessions support the contracts in the ledger. They are not additional production kernels. Public logic functions and lemmas, such as `kafka_rank`, `local_retention_model`, or `lemma_two_sites_never_survive`, state a row's rule and are named in its contract cell where the rule matters. ## Run the Creusot Proofs

The [`.creusot-version`](../.creusot-version) file pins the Creusot release.
That release pins the Rust nightly that `creusot-rustc` needs. Its
`creusot-setup/src/tools_versions_urls.rs` file pins the prover binaries and
checksums. Its `creusot-deps.opam` file pins Why3 and Why3find. The local
[`why3find.json`](../why3find.json) file selects the provers and sets the time
limits, search depth, tactics, and proof-search profile. It does not set a
memory limit.

Install the pinned Creusot release and its provers as the
[`proofs` job](../.github/workflows/ci.yml) does. Then run these commands from
the repository root:

```sh
aspect check-creusot-packages
export PATH="${HOME}/.local/share/creusot/bin:${PATH}"
packages=(krabka-verified)
for package in "${packages[@]}"; do
  cargo creusot --package "${package}"
done
```

The package check fails if a workspace package that depends on `creusot-std`
or contains a Creusot contract is absent from the explicit proof list. It runs
outside the proof image, which carries no Aspect CLI, and it also asserts that
[`tools/creusot/prove.sh`](../tools/creusot/prove.sh) -- the image's entrypoint,
and the loop above -- still names the same packages, so the list and the proofs
cannot drift apart. Each `cargo creusot` command updates its package directory under `verif/`.

`cargo creusot` exits with a nonzero status when any goal is unproved. A deliberately false `#[ensures]` makes the run end with `Error: <n> unproved files` and exit status 1, and `prove.sh` runs under `set -euo pipefail`. An unproved goal therefore fails the CI proof job. CI checks that proof result, not a clean Git diff. Generated `.coma` files contain an absolute source path, so another checkout can change them without a change to the proof result.

Every unique-state count cited below is asserted by the model's own runner
against a `PINNED_UNIQUE_STATES` constant -- one per config where a runner
drives several -- and not merely recorded here. An exhaustive breadth-first
search over a fixed model visits a deterministic set of states, so the exact
count is a checkable fact rather than a bound. The generated-transition count
is not pinned anywhere: it depends on when the search's worker threads
deduplicate, and so varies between runs of the same model.

To change a pin, run the model, read the count the runner prints, and write
that number into the constant. A changed count is a changed model, never a
retuning knob, so a pull request that moves one must say which transition,
action, or state field was added or removed to move it. A count that shrinks
with no such explanation is the failure this pin exists to catch: an action
generator that dropped a branch, a `next_state` arm that began returning
`None`, or a derived `Hash` that stopped considering a field, each of which
leaves a smaller search still passing every upper bound.

The paragraphs below take the entry points in table order. Each one names the production code the model drives, what it models instead, its bounds, its properties and reachability witnesses, and its pinned counts, and it ends with what stays outside the model.

### Broker Data and Fetch

The data-path model ([`data_path_model`](../crates/broker/src/data_path_model.rs)) composes the production HWM core (`ReplicaState`), whose high watermark stands still while the ISR is under `min.insync.replicas` as Kafka's `Partition.maybeIncrementLeaderHW` does, the leader's ISR expansion kernel (`isr_candidate_selected`), the leader-epoch truncation lookup (`epoch_and_offset_for_entries`), the controller failover decision (`failover_one`), the KIP-966 recovery election (`select_leader`), the KIP-966 ELR maintenance rule (`next_partition_elr`), fetch visibility (`compute_visibility_window`), and, on the diskless path, the WAL-durable HWM and the controller's offset reservation (`reserve_offsets` over the image's `PartitionOffsetAdvance` counter). It checks three brokers, one partition, and at most three leader epochs. `data_clean` (strategy None, unclean disabled, log length 4) reaches exactly 521,626 unique states and requires `committed_durable` and `no_loss_when_clean`. `data_unclean` (Balanced recovery, unclean enabled, log length 4) reaches exactly 1,255,681 and requires `committed_durable` while witnessing `unclean_loss`. `data_elr` (`min.insync.replicas` 2, log length 3) reaches exactly 2,795,492; the real ELR set is handed to `failover_one`, so a partition whose live ISR empties elects a surviving ELR member cleanly, and each election is applied by the rule that chose it: an ISR election truncates nothing and is checked by `committed_durable`, an ELR member must hold, and an ELR election must keep, every record that reached the HWM (`elr_holds_every_committed_record`, `elr_election_keeps_every_committed_record`), and only an election reported as losing data sets `lost`. Anti-vacuity witnesses require a high watermark held back by min ISR while every ISR member holds a later record (`hwm_held_by_min_isr`), an ELR to be published, an ELR election to happen, and one to pass over a strictly longer surviving log. `data_diskless` reaches exactly 450 and requires that a WAL-acknowledged record is never lost, that the HWM is released by WAL sync alone, and that reserved offset ranges are gap-free and unique. All four are pinned by `PINNED_UNIQUE_STATES_*` in [`data_path_model/runner.rs`](../crates/broker/src/data_path_model/runner.rs), below the depth-70, 60,000,000-generated, and 8,000,000-unique guards. Record payloads, transactions, remote storage, multiple partitions, and the last-known-ELR half of KIP-966 remain outside the model.

The producer-state model ([`producer_state_model`](../crates/broker/src/producer_state_model.rs)) drives the host's retained-batch bookkeeping (`ProducerEntry::retained_batches` and `earlier_after_append`) and `check_retained` around the proved `producer_decision`, for one producer ID over one- and two-record batches. It compares every answer with an independent classification by Kafka's rules over a ghost window of the five batches Kafka retains (`NUM_BATCHES_TO_RETAIN`), and the `decision_matches_kafka` property turns any disagreement into a counterexample. Witnesses require a duplicate of the last, of an older, and of the oldest of five retained batches, an out-of-order refusal of a retry below a full window, and an epoch bump. The basic config (epochs 0 and 1, sequences through 6) and the wide config (epochs through 3, sequences through 9) reach exactly 731 and 4,233 unique states, pinned by `PINNED_UNIQUE_STATES_BASIC` and `PINNED_UNIQUE_STATES_WIDE`, below the depth-40 and 2,000,000-state truncation guards. The broker serializes one producer's requests, so the model enumerates submit sequences rather than concurrent requests; offsets, snapshots, and transactions remain outside the model.

The replica-state model ([`replica_state_model`](../crates/broker/src/replica_state_model.rs)) holds the production `ReplicaState` and drives its `install_isr`, `update_follower_leo`, and `recompute_hw_for_leader_append` for one partition with three replicas, a fixed leader, and log ends through 3. It explores every interleaving of leader append, follower fetch, and ISR installation. A follower's reported log end never regresses, and an ISR expansion admits only a follower whose log end reached the high watermark, the high-watermark half of Kafka's `Partition.isFollowerInSync`. ISR changes are explicit actions rather than timed decisions, so the lag rule is not checked here. Properties require the high watermark to stay nonnegative and inside the leader's log, every ISR member to hold every committed record (`no_data_loss`), follower log ends clamped to the leader's, and the leader in the ISR; a transition check requires a nondecreasing high watermark. Witnesses cover an advanced high watermark, one that reaches the leader's log end, one held below it by a lagging member, and an ISR shrink. The `isr_safety` config and the `isr_overshoot` config, whose followers may report a log end past the leader's to exercise the clamp, each reach exactly 174 unique states, pinned by `PINNED_UNIQUE_STATES_SAFETY` and `PINNED_UNIQUE_STATES_OVERSHOOT`, below the depth-80 and 200,000-state truncation guards. Wall-clock lag, the controller's `AlterPartition` path, and I/O remain outside the model.

The fetch-session model ([`fetch_session_model`](../crates/broker/src/fetch_session_model.rs)) drives the production KIP-227 forget-then-merge composition `apply_incremental` over sequences of incremental fetches, starting from a fully resolved session. The Fetch visibility model ([`fetch_visibility_model`](../crates/broker/src/handlers/fetch_visibility_model.rs)) drives the production `compute_visibility_window` over advancing partition watermarks, kept in Kafka's order `0 <= log_start <= lso <= hw <= log_end` with KFC-1's `log_start <= deliverable <= hw`. ### Broker Failover and Placement

The assignment is `[1, 3, 2]`, so ISR order and assignment order differ. ### Log

The compaction model ([`compact_model`](../crates/log/src/compact_model.rs)) runs one pass of a cleaner over an abstract log per `Compact` step, the production `should_index_key` and `retain_decision` by default, and records the log the pass consumed in the next state. Five `always` properties check each pass's output against its input with rules computed from the two logs alone: control-not-deduped (a marker whose horizon has not elapsed survives), marker-data-precedence (a marker survives while the pass reads data of its own transaction in front of it, as Kafka decides per transaction rather than per producer), tombstone-aging (no elapsed tombstone survives; an unexpired newest tombstone does), idempotent-stamp (the output is the input with deletions and `None -> now + delete.retention.ms` stamps only), and no-data-loss (the set of keys with a live newest value is unchanged). The basic run (logs up to 4 entries) and the wide run (up to 5) reach exactly 144,128 and 1,102,770 unique states, pinned by `PINNED_UNIQUE_STATES_BASIC` and `PINNED_UNIQUE_STATES_WIDE` in [`compact_model/runner.rs`](../crates/log/src/compact_model/runner.rs), below the depth-40 and 1,500,000-unique guards. The legacy cleaner, which indexes control keys and dedups markers by them, is run through the same pass and checker, which reports exactly control-not-deduped and marker-data-precedence as broken, with the recorded five-action counterexample.

The leader-epoch reconciliation model drives the production [`epoch_and_offset_for_entries`](../crates/verified/src/leader_epoch.rs) lookup on both sides of a fetch and the production checkpoint truncation (`truncate_to`), with Kafka's `LeaderEpochFileCache.assign`, `Partition.readRecords` divergence gate, and `AbstractFetcherThread.getOffsetTruncationState` follower rules as the environment. Replicas hold logs of per-offset leader epochs; elections are clean or unclean, and the new leader assigns its epoch at its log end. The `reconciliation_two_replicas` config (two replicas, epochs through 5, three records per leader log) reaches exactly 35,274 unique states, and `reconciliation_three_replicas` (three replicas, epochs through 3, two records) exactly 20,212, pinned by `PINNED_UNIQUE_STATES_TWO` and `PINNED_UNIQUE_STATES_THREE` in [`leader_epoch_model`](../crates/log/src/leader_epoch_model.rs), below its depth-64 and two-million-state truncation guards. Properties require a follower the leader has accepted to be a prefix of the leader's log, no truncation to drop a record the follower shares with the leader, every `diverging_epoch` to change the follower (no livelock), the leader never to answer `OFFSET_OUT_OF_RANGE`, and every checkpoint to stay strictly increasing. Reachability witnesses cover a divergent suffix really truncated, a gap epoch resolved to the leader's floor epoch, a KIP-279 step-back round, and full convergence after a divergence. A third config (two replicas, epochs through 4, three records; 10,865 unique states, `PINNED_UNIQUE_STATES_NO_ASSIGN`) drops assign-at-election and must find a counterexample to `leader_places_every_follower_epoch` while the safety properties still hold: without it a newly elected leader that has not written cannot place a follower's newer epoch. The broker assigns the epoch at promotion, as `Partition::install_local_leadership` records it at the log end, so the first two configs describe production and the third is the regression the assignment prevents. Replacing the gap branch's floor epoch with the requested epoch fails the proptest driver described next. A [proptest driver](../crates/log/src/leader_epoch_checkpoint/fuzz.rs) runs the same step function over random 400-step schedules on four replicas. Log start above 0, tiered storage, the below-log-start `OFFSET_OUT_OF_RANGE`, the follower's `ListOffsets`-based out-of-range recovery, wire encoding, and I/O remain outside the model.

### KRaft

The `KRaft` model ([`kraft_model`](../crates/raft/tests/kraft_model.rs)) runs the production `QuorumStateMachine` for every node over an unordered network. Replication is the one abstracted exchange: the records a fetch returns are applied when the follower sends it, and only when the leader's log extends the follower's (the high watermark reaches a follower on the same terms). A follower whose log disagrees with the leader's is never overwritten; the production `handle_fetch` answers its fetch with a diverging epoch, the production `handle_fetch_response` truncates it, fetches again at once from the truncated end, and re-arms the fetch timer, as Kafka's `KafkaRaftClient.handleFetchResponse` and `pollFollowerAsVoter` do, and the `divergent_log_truncated` witness requires that path to run in both crash configs. Its `three_voters_append` config checks leader completeness under a stale majority: three voters, one client append, leader epochs through two, at most two in-flight messages, and at most one crashed node at a time, whose omission model drops that node's traffic and so leaves it behind the committed prefix. The pinned run reached 457,067 unique states, asserted by `PINNED_UNIQUE_STATES_THREE_VOTERS_APPEND`, below its depth-60 and 6,000,000-state truncation guards. The `leader_completeness` property requires every node that believes it leads epoch `e` to hold each entry committed in an epoch at or below `e`, stamped with the epoch it committed under. The `stale_candidate_refused` witness requires a vote refused for log recency alone: the transition that delivers the request also runs a copy of the voter's real machine on the same request with the candidate's log end replaced by the voter's own, and only a refusal that copy grants counts. It would disappear if the config stopped reaching a stale-majority election. Removing the log-recency conjunct from `handle_vote_request` makes this config fail. The other configs cover election and log-matching safety with three voters and no appends (`three_voters_election_safety`, 10,834 states), committed-log linearizability with two voters (`two_voters_linearizable`, 43,811), election safety under message loss, duplication, and one crash at a time (`three_voters_faults`, 777,338), and stateless appenders (`two_voters_append_via_linearizable`, 230,591), each pinned by its `PINNED_UNIQUE_STATES_*` constant. Wire encoding, disk durability, wall-clock timing, volatile-state loss on restart, and behavior beyond the stated bounds remain outside the model.

### Throttle

The throttle bucket model drives the production [`plan_consume`](../crates/verified/src/throttle.rs) cap-and-grant arithmetic at every commit and steps the [`TokenBucket`](../crates/throttle/src/runtime.rs) protocol one shared-memory access at a time: the lock-free rate-mirror read of the unthrottled fast path, the lock acquire, the clock read, the `last_refill` claim, the `available` commit, and the release for a consume; the lock acquire, the group store, the mirror publish, and the release for a reset, with a separate burst per configuration. A reset keeps the balance: it refills the old configuration to now, caps the balance at the old and then at the new burst, and starts a bucket that had no rate, or gets none, full. Its `bucket_basic` config checks two consumers, one reset between bursts 2 and 1, two clock units, and requests up to two; the run reaches exactly 56,259 unique states, pinned by `PINNED_UNIQUE_STATES_BASIC`. Its `bucket_wide` config checks two consumers, two resets among `(rate 1, burst 3)`, `(2, 1)`, `(0, 0)` and `(1, 0)`, two clock units, and requests up to two; the run reaches exactly 372,204 unique states, pinned by `PINNED_UNIQUE_STATES_WIDE`. Its `bucket_fractional` config meters two storage units to a token, as production meters micro-tokens, and checks two consumers, one reset from `(rate 1, burst 3)` to `(1, 1)`, two clock units, and requests up to two whole tokens, so its rates are half a token per second and the second burst holds half a token; the run reaches exactly 33,964 unique states, pinned by `PINNED_UNIQUE_STATES_FRACTIONAL`. Each commit also drives the production whole-token request cut, [`whole_token_request`](../crates/throttle/src/runtime/consume.rs). All three stay below the depth-80 and 4,000,000-state truncation guards. Properties require `available <= burst` and exact token conservation per configuration: `available + granted + capped + in-flight claimed refill == base + rate * (last_refill - t0)`, where `base` is the balance the reset started the configuration with, so a claimed refill can neither vanish nor be granted twice, and every grant is a whole number of tokens. Reachability witnesses cover overlapping consumers, a reset overlapping a consume, an in-flight claim, a granted and a capped refill, a shrinking reset, a drained bucket, and a reset that keeps a balance under the new burst. Debt is outside the model: `try_consume` never creates it, and `record` differs from a consume only in what it does with the part it cannot grant, which it keeps as debt, at most what the refill repays in `max_wait` for `record_bounded`; the unit tests in [`consume.rs`](../crates/throttle/src/runtime/consume.rs) cover both. RED witnesses step the former lock-free seqlock design (a generation re-check followed by two compare-and-exchanges) and must find both of its bugs: a whole reset between the generation re-check and the `available` commit that lets `available` exceed the new burst, and a failed commit that drops the refill its claim took. Two scripted schedules replay each bug concretely against the seqlock and show that the lock makes the same interleaving impossible. The clock is modeled in whole seconds with rates in whole storage units and memory as sequentially consistent; the part-unit remainder is covered by unit tests in [`consume.rs`](../crates/throttle/src/runtime/consume.rs).

### Audit

The audit spool model ([`spool_model`](../crates/audit/src/spool_model.rs)) drives the production `spool_append_decision` for every spool append, a record's or a loss marker's, the `add_loss_state` helper behind `PendingLosses::add`, the `settle_loss_batch` kernel that `PendingLosses::commit` and `PendingLosses::reconcile` apply, and the replay-recovery classifier behind `Spool::open`. The loss path is `PendingLosses` as the serial writer drives it: a concurrent `AuditHandle::emit` loss or a crash can fall between any two of `persist_with`'s steps (snapshot, sidecar write, marker append subject to spool capacity, sync, in-memory commit, commit write), and a poisoned reopen stops before reconciliation as `Spool::open` does. It checks three record IDs, two loss events, a two-record spool, sync cadence two, and at most two crashes, in every reachable ordering. The run reaches exactly 71,351 unique states, pinned by `PINNED_UNIQUE_STATES` in the model file, below its depth-64 and 4,000,000-state truncation guards. Properties require every durably admitted record to remain delivered or durably pending, at-most-once automatic delivery, exact loss accounting (every loss is reported by exactly one durable marker, is still pending, or was held only in memory at a crash), distinct marker generations, and every durable marker settled exactly once. Reachability witnesses cover torn append recovery, retry after a definite sink failure, fail-stop poison after an uncertain delivery, cleanup after a committed cursor, a marker refused by a full spool, loss-marker reconciliation after reopen, and a concurrent loss carried past a marker. The test `superseded_settlement_loses_and_rereports_losses` keeps the settlement that `PendingLosses` applied before `settle_loss_batch`, in which a commit left the remainder in the marker's generation and reconciliation zeroed the whole count, and requires the checker to find `losses_accounted`, `marker_generations_unique`, and `markers_settled_once` counterexamples for it. Filesystem and directory-sync semantics, storage hardware, sink durability, explicit operator recovery of poisoned replay, and behavior beyond the stated bounds remain outside the model. Adapter tests cover malformed, missing, stale, and committed poison plus loss-counter saturation.

## Outside Both Tiers

Code that is not in the Creusot ledger or the Stateright inventory is in
neither tier. This includes most protocol encoding and decoding, authorization,
network and async orchestration, file and object-store I/O, and operational
configuration. Unit, property, integration, differential, and container tests
cover those areas. Those tests are evidence, but they are not a Creusot proof
or a Stateright model check.

The barrier coordinator's [`__barrier_state` partitioner](../crates/broker/src/barrier/partitioner.rs) is the one coordinator routing decision without a proof. It applies Kafka's `Utils.abs(murmur2(bytes)) % numPartitions` over the group name through the broker's own `murmur2`, and JVM golden vectors test it. The group, transaction, and SHARE coordinator partitioners route through the proved `java_string_hash_partition`, and the KIP-405 metadata partitioner through `remote_metadata_partition`.

A proved kernel does not prove its caller. The proof starts after the caller
establishes the preconditions in the ledger. A Stateright model does not prove
the I/O around the decisions that it drives.
