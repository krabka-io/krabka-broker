# Operations

The operator guide for krabka-broker: what to deploy, what to watch, and
what to do when an alert fires. Everything here describes the broker on this
branch. Where a document names a flag, a config key or a series, that name is
the one the code reads, and the [contract check](metrics.md#the-contract-check)
fails the build when the series drift.

## Guides

- [Deploy](deploy.md): install the image or the binary, format a log
  directory, write the config file, start, stop and roll a cluster.
- [Capacity](capacity.md): what a broker spends per partition and per byte,
  how to size disk, network and voters, and how to read the phase families.
- [Metrics](metrics.md): every exported series with its labels and the JMX
  name it replaces.

## Monitoring

- [`grafana-dashboard.json`](grafana-dashboard.json): a reference Grafana
  dashboard. Import it and pick the Prometheus datasource it asks for.
- [`alert-rules.yaml`](alert-rules.yaml): Prometheus alert rules with the
  thresholds the metric doc comments recommend. Each rule names its runbook.
- [`metrics-body.txt`](metrics-body.txt): a `/metrics` body with one label
  set per family, generated by the `metrics_contract` test suite. It is what
  the CI docs job checks the dashboard and the rules against.

## Keeping the contract

`tools/check-metrics-contract.py docs/operations/metrics-body.txt` fails on
any series the dashboard or the rules name that the body does not carry.
`bazel test //crates/broker:metrics_contract_test` runs the same check
against a live registry and fails when `metrics-body.txt` is stale. When a
family changes, regenerate the body, then update [metrics.md](metrics.md),
the dashboard and the rules in the same change.
